# 麦麦黄历 · maimai-almanac

> 黄历的第一问不是「我有什么」，是「今天是什么日子」。

<a href="https://github.com/chinahui/maimai-almanac/blob/main/docs/screenshot-pixel.png"><img src="https://cdn.jsdelivr.net/gh/chinahui/maimai-almanac@main/docs/screenshot-pixel.png" width="420" alt="麦麦黄历 · 今日判决卡片"></a>

基于麦当劳 MCP 的每日历书。每天只回答两件事：**今天是什么日子，所以你该先动哪一个。**

卡片按手机屏幕设计：1080×1440（3:4），四层信息，三秒看完。

## 黄历有两条腿

真正的黄历只有两层：

| 层 | 回答什么 | 数据来源 |
|---|---|---|
| **天时** | 今天是什么日子：第几波活动、开售第几天、下一波什么时候 | `campaign-calendar`，公共的 |
| **人事** | 今天宜什么、忌什么 | 由天时推出来，落到你的账户上 |

黄历之所以成立，是因为**天时在前，人事在后**。
你翻黄历不是为了看自己家有几亩地，是为了知道今天是个什么日子。

**你的券和积分不是主角，是那句「冲什么」的注脚。**

黄历处理个人化的方式也是这个：它不把你的八字摊开，只说「今日冲兔」。
属兔的人自己知道该怎么办。账户数字同理——它只负责让「宜清券」这句话有落点。

## 为什么需要它：资产会腐烂

麦麦账户里躺着三种**会归零的资产**：券有有效期、积分有到期批次、活动场次有预约截止。

已经有一百多个工具帮你**找到**这些资产。没有人帮你决定**先用哪个**。

结果是：券过期了才想起来，积分在账户里慢慢腐烂，活动错过了才发现。

看看下面这组数字（示例账户）——它就是黄历每天要处理的东西：

| | |
|---|---|
| 可用的券 | 3 张，**1 天后全部到期** |
| 可用积分 | 1250 |
| **已经过期作废的积分** | **480** |

480 分，按商城最优兑换率折算，差不多是三个汉堡。
它们不是被花掉的，是被忘掉的。

麦麦黄历每天回答一个问题：**今天，我手上这些东西，先动哪一个。**

## 它的世界观：先止损，再优化

大多数省钱工具在算「怎么买最便宜」。这个问题的前提是「你一定会买」。

但真实情况是：一张 3 天后过期的 5 元券，价值**高于**任何「再等 7 天省 4 块」的优化。
因为前者是确定的损失，后者是概率性的收益。

所以判决的第一优先级永远不是最优价格，而是**什么正在腐烂**。

这条原则叫 **decay-first（资产腐烂优先）**，是整个项目的内核。

## 今天的「日子」是怎么判出来的

`campaign-calendar` 一天能返回十几条活动，大部分是长期在跑的常规促销，不构成「日子」。
要挑的是**今天独有**的那一条。挑法就是择日的逻辑：

```
第 N 弹 / 限量周边 / 联名  >  上新  >  常规促销  >  什么都没有
```

实际跑出来是「周边第二弹——联名徽章正式发售」，正文写「10月15日10:45开售」，
所以今天是**在售第 7 日**。

这一步的产出不是活动标题，是**你在时间轴的哪儿**：

| 字段 | 今天实际值 |
|---|---|
| 阶段 | 发售期 · 第 7 日 |
| 主场 | 周边第二弹 · 联名徽章 |
| 开售 | 10月15日 10:45 开售 · 加 ¥39.9 可得 |
| 同场 | 14 场，取前三 |
| 换气 | 1 天后 · 10-22 · 第三周周边限定主题丝巾 |

少了「第几日」和「下一波」，天时就只是一个活动标题——读者知道今天有事，但不知道自己在时间轴的哪儿。

## 人事：宜忌怎么来的

同一份数据，四类判断：

| 判断 | 依据 | 今天实际输出 |
|---|---|---|
| 宜 · 清券 | 券的剩余天数 ≤ 3 | 「11.9 元指定汉堡」只剩 2 天 |
| 宜 · 兑换 | 兑换率 ≥ 中位数的 1.5 倍 | 50 分换 6.9 元可乐，每分 0.138 元，中位数的 2.5 倍 |
| 忌 · 囤券 | 多张券同时临近到期 | 2 张券都在 2 天内到期，别再领新的 |
| 忌 · 加购 | 活动文案含「加 X 元即可得」 | 加 ¥39.9 才得周边，非必需就别凑 |

外加一条 **今日最坑**：800 分只换到 21.9 元的组合，每分 0.027 元，只有最优档的 20%。

**每一条判决都带数字和数据来源工具名。** 没有依据的判断不会出现在历书上。
格式是玄学，内核是账本。

## 三个真实的坑，和它怎么处理

做这个项目最大的收获不是调通 API，是发现 MCP 返回的数据不能直接信。
三个坑都写进了代码，也写在卡片外面的注释里：

**① 已下架的商品，状态仍是「上架」**

`mall-points-products` 返回 19 个积分商品，其中 **12 个的 `downTime` 早已过期**
（最早的是 2026-03-21），但 `status` 全部还是 2（上架）。

第一版算法兴高采烈地推荐了「50 分换 18.8 元两件套」——一个七个月前就失效的商品，
兑换率 0.376 元/分，漂亮得不像真的。

> 现在的做法：不信 `status`，只信 `downTime > now`。

**② 积分商品的面值不在 `price` 字段里**

积分商品的 `price` 恒为 `0`，真实面值只写在名称里（「18.8元2份麦辣鸡翅」）。
不解析名称，所有商品的兑换率都会算成 0。

**③ 返回的不是 JSON**

`campaign-calendar` 和 `query-my-coupons` 返回的是给人看的 markdown；
账户、商城、抽奖则在 `## Original Response` 里附原始 JSON。
两套格式，两套解析器，缺一不可。

这三条让「兑换率」这个指标从 0 变成可用。也说明一件事：
**MCP 是通道，不是答案。**

## 它会自己变聪明

`campaign-calendar` 的时间线窗口很窄——实测只能看到 **2026-10-20 到 11-03**，
往前往后都查不到。所以这个项目**不假装自己懂历史周期律**。

它每天在**本地**存一份快照：

```
data/snapshots/2026-10-21.json
data/snapshots/2026-10-22.json
```

> 这些文件**不会进仓库**。快照里有账户积分余额和券名，属于个人信息，
> 已经写进 `.gitignore`。仓库里只放一份脱敏的 `data/snapshots.example.json` 说明结构。

跑满 30 天，它自带一条真实的活动时间线，那时「哪天值得等」才是被数据支撑的。

**它不假装一开始就懂，它只是每天都在记。**

## 安装

```bash
git clone https://github.com/<you>/maimai-almanac
cd maimai-almanac
cp .env.example .env        # 填入 MCD_MCP_TOKEN
```

Token：[open.mcd.cn/mcp](https://open.mcd.cn/mcp) → 手机号登录 → 控制台 → 激活。

依赖：Python 3.9+（标准库即可运行），出图另需 Node + Playwright。

## 使用

```bash
# 探针：先确认工具连通、字段长什么样
python src/probe.py --schema-only

# 今日判决（终端）
python src/almanac.py today

# 出图（默认像素风手机卡片，1080×1440）
python src/almanac.py today --png out/today.png

# 换成竖排宣纸风格（1080×1440，适合电脑看）
python src/almanac.py today --style classic --png out/classic.png

# 归档今日快照
python src/almanac.py snapshot

# 静态页
python src/almanac.py build --out out
```

## 目标用户

- **每周吃 3 次以上**的重度麦门，账户里常年压着券和积分
- **被券的过期日追着跑**的人，总觉得「好像有张券还没用」
- **做消费类内容**的创作者，需要每天一条可发布的素材

## 已知边界

- 判决只覆盖**资产维度**（券 / 积分 / 活动），不含实时价格试算
- 数据不足时**不编**周期律，直接写「历史不足」
- 不提供营养或医疗建议
- 抽奖相关只算期望值，措辞中性，不构成参与建议
- 个人数据（券码、订单号、地址、账户余额）永不入库；快照只在本地生成

## 卡片为什么是这个样子

同一份判决有两种呈现，面向不同场景：

| 风格 | 尺寸 | 场景 | 做法 |
|---|---|---|---|
| `pixel`（默认） | 1080×1440 | 手机相册、朋友圈、小红书 | 麦当劳红黄、硬边阶梯阴影、像素点阵 |
| `classic` | 1080×1440 | 电脑阅读、README | 竖排宋体、宣纸、印章 |

像素风的取舍值得说明：**中文没有可用的小字号像素字体**，硬套点阵字体会糊成马赛克。
所以像素只做「界面语言」——硬边框、阶梯阴影、点阵底纹、8-bit 图标（用 SVG 方块手排），
正文仍然用苹方，保证小屏可读。

判词不拆成多条短句，而是压成**一整个黄底菜单牌**。
因为手机上第一眼只该看见一个结论，拆碎了就成了"信息"，不再是"判决"。

### 信息层级不能倒

卡片从上到下是四层，顺序就是黄历的顺序：

| 层 | 内容 | 占的高度 |
|---|---|---|
| 天时 | 今天是什么日子 | 最大 |
| 人事 | 宜 / 忌 | 次之 |
| 判词 | 一句话收口 | 中等 |
| 卦象 | 账上多少分、多少券 | **最小，一行小字** |

「账上已经腐掉多少分」很有冲击力，但它是**复盘**，不是**告诫**。
黄历不会说「你亏了多少」，它说「今日忌破财」。
所以那三个数字从整屏大数字，降成了最底下一行注脚——它是证据，不是结论。

