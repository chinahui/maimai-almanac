# 麦麦黄历 · 设计说明

## 一、这个项目要解决什么

已有一百多个麦麦工具在帮你「找到券」。**没有人帮你决定「今天到底该不该下单」。**

信息过剩不会让人省钱，只会让人拖延。用户真正缺的不是券列表，是一个**判决**——
以及一个能让他相信这个判决的理由。

麦麦黄历每天给你一张历书，上面只有一件事：今天宜做什么、忌做什么，为什么。

## 二、为什么是「判决」而不是「信息」

| | 常见省钱工具 | 麦麦黄历 |
|---|---|---|
| 输入 | 你问「有什么券」 | 不问，每天自动出 |
| 输出 | 券列表 + 折扣率 | 一条带数字的判决 |
| 心理机制 | 你自己算，算完还是不确定 | 替你承担决策成本 |
| 使用节奏 | 想起来了才用 | 每天一张，形成习惯 |
| 失败模式 | 券过期了才想起来 | 过期前一天会被提醒「忌」 |

## 三、核心模型：资产腐烂优先 + 四路比价

### 3.1 资产腐烂优先（decay-first）

麦当劳账户里的钱有三种形态，都会归零：

- **券**：有有效期，过期即废，价值归零
- **积分**：有到期批次，过期扣减
- **活动场次**：有预约截止时间，错过不补

所以判决的第一优先级**永远不是「怎么买最便宜」，而是「什么正在腐烂」**。
一张 3 天后过期的 5 元券，价值高于任何「再等 7 天省 4 块」的优化——
因为前者是确定的损失，后者是概率性的收益。

这条原则是整个产品的世界观：**先止损，再优化。**

### 3.2 四路比价

对同一笔需求（餐品集合 `S`、门店 `st`），同时算四条路径：

| 路径 | 数据来源 | 计算 |
|---|---|---|
| ① 原价买 | `calculate-price` | `P_list = price(S, st)` |
| ② 用券买 | `query-store-coupons` / `query-my-coupons` | `P_coupon = min over coupons` |
| ③ 积分换 | `mall-points-products` + `query-my-account` | `P_points = 所需积分 × 单位积分基准价` |
| ④ 等一等 | `campaign-calendar` 未来活动 | `P_wait = P_list × (1 − 已知活动折扣率)` |

判决逻辑：

```
P_now  = min(P_list, P_coupon)
若 存在腐烂资产          → 宜清券 / 宜兑换（压倒一切）
否则若 P_now <= P_wait×(1+θ) → 宜下单
否则若 等待天数 <= 耐心阈值 → 宜等待（给出倒计时）
否则                     → 宜下单
```

### 3.3 积分兑换率基准

`兑换率 = 商品市场价 ÷ 所需积分`。取商城全部商品兑换率的**中位数**作为基准线。
高于基准 = 这单积分花得值；低于基准 = 亏，并给出「亏多少 %」。

这让「积分该换什么」从一个模糊感觉变成一个可比较的数字。

### 3.4 可解释性

每一条宜/忌都必须携带 **数字 + 数据来源工具名**。不允许出现没有依据的判断。
这是这个项目和玄学类项目的分界线：**格式是玄学，内核是账本。**

## 四、数据会自己长出来

`campaign-calendar` 的时间线窗口很窄。**实测（2026-10-21）窗口约为 2026-10-20 至 11-03**，
用 `specifiedDate` 可以沿时间线逐日爬行覆盖整个窗口，但窗口之外一律返回空——
往前查不到 9 月，往后查不到 11-10。

所以「靠历史挖周期律」在起步阶段**不成立**，不要用推测绕过。

解法是**每日快照归档**：

```
data/snapshots/2026-10-21.json   ← 当天活动日历 + 券 + 积分的结构快照
data/snapshots/2026-10-22.json
...
```

每跑一次就多一天。运行 30 天后，项目自带一条真实的活动时间线，
届时「周期律」才是被数据支撑的，而不是编的。

**这也是项目最诚实的卖点：它不假装自己一开始就懂，它只是每天都在记。**

快照中的个人账户数据（券、积分）在落盘前统一脱敏，只保留聚合量。

## 五、形态

### 5.1 历书卡片（竖排）

仿传统历书版式，`writing-mode: vertical-rl`，六格结构：

```
        ┌──── 丙午年 · 十月 · 廿一日 ────┐
        │        麦 麦 黄 历            │
        ├────────┬────────┬─────────────┤
        │  宜    │  忌    │ 券 2张/3天  │
        │ 下单   │ 囤券   │ 分 3,820    │
        │ ...    │ ...    │ 场 无       │
        ├────────┴────────┴─────────────┤
        │ 今日最坑：积分换小薯，亏 40%   │
        │ 据 campaign-calendar 等 4 源   │
        └───────────────────────────────┘
```

### 5.2 三个出口

1. **CLI**：`python -m almanac today` → 终端直接打印，也导出 PNG
2. **静态页**：每日生成 `out/index.html`，可部署，可分享
3. **WorkBuddy Skill**：`SKILL.md` 让 AI 直接调用，对话里出黄历

## 六、明确不做什么

划清边界，避免退化成又一个同质化工具：

- ❌ 不做「全网比价」——只用麦当劳自己的 MCP 数据，不引第三方
- ❌ 不做历史周期律预测——数据不足时不许编
- ❌ 不做营养/医疗建议——只做价格与资产决策（合规声明要求）
- ❌ 不做抽奖「攻略」——只算期望值，措辞中性，不鼓励参与
- ❌ 不追求功能数量——宁可 3 个判断做准，不要 20 个功能做浅

## 八、风险

| 风险 | 应对 |
|---|---|
| 券/积分字段拿不到有效期 | 降级：只做「券数量 + 面额」维度，腐烂提醒改用活动截止时间 |
| `campaign-calendar` 未来数据太稀 | 降级：④ 路比价退化为「无已知活动」，判决只依赖 ①②③ |
| 个人账户数据难以脱敏 | 快照只存聚合统计量，不存券码、订单号、地址 |
| 4 天做不完 | 砍静态页，保 CLI + PNG，因为图才是传播物 |

## 九、实测校正（2026-10-21）

拿到 Token 后跑完探针，有四处设计假设被现实修正，记录在此以免后来者重踩。

| 原假设 | 实测结果 | 处理 |
|---|---|---|
| 活动日历至少覆盖当月 | 窗口仅 10-20 ~ 11-03，过去不可回溯 | 放弃周期律预测，改为每日快照积累 |
| 积分商品 `price` 可作面值 | 积分商品 `price` 恒为 0，面值在名称里 | 从 `spuName` 提取「X 元」 |
| `status=2` 即上架 | 19 个商品中 12 个 `downTime` 已过期但仍是 2 | 只信 `downTime > now` |
| 活动文案价格可用 | 混入日均价（0.33 元/天）与权益价（9.9 元咖啡） | 卡片不再展示按活动抽的价格，改用类型标签 |

第 3 条影响最大：修正前算法推荐「50 分换 18.8 元」，兑换率 0.376 元/分，全表最高——
但那是一个 2026-03-21 就已下架的商品。**错误的数据往往比没有数据更有说服力。**

修正后真实兑换率区间为 0.027 ~ 0.138 元/分（约 5 倍差距），中位数 0.054。

### 对「四路比价」的收窄

v0.1 只做了③（积分）与④（活动）两路，①②（原价买 / 用券买）依赖
`query-meals` + `calculate-price` 的精确试算，尚未接入。

因此当前判决**不含实时价格比较**，是纯粹的资产决策器。
这是有意的取舍：4 天内把两路做准，好过把四路都做浅。
